# Orchestrator–worker and spec-driven development patterns for AI coding-agent "teams" (state as of late 2026)

Scope note: research conducted 2026-11-01. Sources are marked **[primary]** (vendor docs, repo READMEs/templates, first-hand retrospectives), **[secondary]** (press/blog summaries of a primary source) or **[anecdotal]** (single practitioner, forum, unverified vendor claim). Anything dated before 2025 is marked **background**. Where a fetched page did not contain a claimed detail, the gap is recorded rather than filled from memory.

---

## KQ1. What does Anthropic's own published guidance say, and which orchestration patterns does it recommend or warn against?

### Takeaway
Anthropic's line is consistent across five posts (Dec 2024 → Mar 2026): start with the simplest workflow, add an orchestrator–worker layer only when subtasks cannot be predicted up front, brief every worker with objective / output format / tools / boundaries, keep the orchestrator's context clean via condensed worker summaries and file-based handoffs, and separate the agent that does the work from the agent that judges it. They explicitly warn that coding has fewer parallelisable parts than research, that multi-agent costs ~15× chat tokens, and that agents overrate their own output.

### Cited Findings

**"Building effective agents" (Dec 2024 — background, still the canonical taxonomy)**
- Defines workflows as "systems where LLMs and tools are orchestrated through predefined code paths" vs. agents that "dynamically direct their own processes and tool usage". — [Anthropic, Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) [primary]
- Orchestrator-workers: "well-suited for complex tasks where you can't predict the subtasks needed"; the difference from parallelization is that subtasks are determined at runtime. Example given: "coding products that change many files". — [same](https://www.anthropic.com/engineering/building-effective-agents)
- Evaluator-optimizer: "particularly effective when we have clear evaluation criteria, and when iterative refinement provides measurable value". — [same](https://www.anthropic.com/engineering/building-effective-agents)
- Core principles: "Maintain simplicity in your agent's design", show planning steps explicitly, "Carefully craft your agent-computer interface (ACI)". Warnings: "find the simplest solution possible, and only increasing complexity when needed"; "The autonomous nature of agents means higher costs, and the potential for compounding errors." — [same](https://www.anthropic.com/engineering/building-effective-agents)

**"How we built our multi-agent research system" (June 2025)**
- Pattern: lead agent plans, spawns subagents in parallel, synthesises; a separate CitationAgent post-processes. Lead saves its plan to memory because context beyond 200k tokens was truncated. — [Anthropic, Multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system) [primary]
- Subagent brief must contain four things: "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries." Vague briefs → one subagent researched the 2021 chip crisis while two others duplicated 2025 supply-chain work. — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
- Effort-scaling rules embedded in the prompt: simple fact-finding = 1 agent, 3–10 tool calls; comparisons = 2–4 subagents, 10–15 calls each; complex research = >10 subagents with clearly divided responsibilities. — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
- Observed failure modes: spawning 50 subagents for simple queries; endless searching for nonexistent sources; "subagents distracting each other with excessive updates"; duplicated work and gaps from unclear division. — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
- Cost: agents ≈4× chat tokens, multi-agent ≈15×; token usage explains 80% of performance variance on BrowseComp. Multi-agent (Opus 4 lead + Sonnet 4 workers) beat single Opus 4 by 90.2% on their internal eval. — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
- Explicit caveat for coding: multi-agent "only pay[s] off for high-value tasks"; coding tasks "with fewer parallelizable parts" are a poor fit. — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
- Architectural limitation: synchronous execution — the lead waits for each batch, "can't steer subagents, subagents can't coordinate, and one slow subagent blocks the system". — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
- Telephone-game mitigation: filesystem artifacts — subagents write outputs to files and pass lightweight references, avoiding information loss when everything routes through the lead and avoiding token overhead of copying large outputs. — [same](https://www.anthropic.com/engineering/multi-agent-research-system)
- Evaluation: single LLM-judge call with a rubric (factual accuracy, citation accuracy, completeness, source quality, tool efficiency) outputting 0–1 score + pass/fail was "the most consistent and aligned with human judgements"; start with ~20 test queries; judge end-state not path. — [same](https://www.anthropic.com/engineering/multi-agent-research-system)

**"Effective context engineering for AI agents" (Sep 2025)**
- Defines "context rot": as token count grows, "the model's ability to accurately recall information from that context decreases"; models have a finite "attention budget". — [Anthropic, Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) [primary]
- Three long-horizon techniques: compaction, structured note-taking (NOTES.md / to-do files outside the window), sub-agent architectures where each sub-agent "returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)". Match technique to task: compaction for long conversations, notes for milestone-driven iterative work, sub-agents for parallel research. — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Warning: "overly aggressive compaction can result in the loss of subtle but critical context". Just-in-time retrieval (keep file paths/identifiers, load at runtime) is slower but avoids pre-loading. — [same](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**"Effective harnesses for long-running agents" (Nov 26, 2025)**
- Two failure modes of naïve long runs: (1) overreach — "the agent tended to try to do too much at once", running out of context mid-feature, "leaving the next session to start with a feature half-implemented and undocumented"; (2) premature completion — a later session saw progress and "declare[d] the job done". — [Anthropic, Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) [primary]
- Harness: an **initializer agent** (first session) writes `init.sh`, `claude-progress.txt`, an initial commit and a JSON feature list (>200 items for a claude.ai clone); **coding agents** in later sessions "make incremental progress, then leave structured updates" and leave code merge-ready. The two agents differ only in their initial user prompt. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Feature-list entry format (verbatim from the post): `{"category": "functional", "description": "New chat button creates a fresh conversation", "steps": ["Navigate to main interface", "Click the 'New Chat' button", "..."], "passes": false}`. Coding agents may only flip `passes`; prompt says "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." JSON chosen over Markdown because models are less likely to overwrite it. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Session startup routine: `pwd`, read git log + progress file, read feature list, pick highest-priority unfinished feature, start dev server via `init.sh`, run a basic end-to-end check before new work. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Verification: Claude often marked features complete without end-to-end checks; explicit instruction to test via browser automation "as a human user would" markedly improved results. — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Open question stated by Anthropic: whether one general-purpose agent beats a multi-agent setup with "dedicated testing, QA, or cleanup agents". — [same](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**"Harness design for long-running apps" (Mar 24, 2026) — the three-agent harness**
- Roles: **Planner** expands a 1–4 sentence prompt into a product spec; **Generator** builds; **Evaluator** tests the running app via Playwright MCP, scores criteria, files bugs. Agents "communicated through files, with one agent writing a file that another reads and answers". — [Anthropic, Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps) [primary]
- **Sprint contracts**: before each sprint the generator proposes what "done" means and how to verify it; the evaluator reviews the contract. Evaluator reports are pass/fail per contract criterion with code locations. — [same](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Self-grading bias: agents "reliably skew positive when grading their own work"; out of the box Claude was "a poor QA agent" that identified real issues then talked itself into approving. Fix: separate evaluator, calibrated with few-shot examples and detailed score breakdowns (reduced score drift); full-stack criteria (product depth, functionality, visual design, code quality) each with a hard threshold — failing any one fails the sprint. — [same](https://www.anthropic.com/engineering/harness-design-long-running-apps); corroborated by InfoQ quoting Anthropic Labs lead: "Separating the agent doing the work from the agent judging it proves to be a strong lever" — [InfoQ, Apr 4 2026](https://www.infoq.com/news/2026/04/anthropic-three-agent-harness-ai/) [secondary]
- Context resets vs compaction: with Sonnet 4.5 (strong "context anxiety") resets with structured handoffs were essential; with Opus 4.5 resets were dropped and the build ran as one continuous session with SDK auto-compaction. — [same](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Cost/quality data: retro game maker, Opus 4.5 solo = 20 min / $9 / core feature broken; full harness = 6 h / $200 / working. DAW on Opus 4.6 with simplified harness = 3 h 50 min / $124.70. — [same](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Design rule: "every component in a harness encodes an assumption about what the model can't do on its own" — remove one component at a time to find what is load-bearing; re-examine on each new model; evaluator "is worth the cost when the task sits beyond what the current model does reliably solo". — [same](https://www.anthropic.com/engineering/harness-design-long-running-apps)

**Claude Code docs — Agent teams (experimental, 2026)**
- Enabled by `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`; one lead per session, teammates have own context, shared task list (states pending / in progress / completed; tasks can depend on others and show as blocked), mailbox JSON at `~/.claude/teams/{team}/inboxes/{agent}.json`; task claiming uses file locking. — [Claude Code docs, Agent teams](https://code.claude.com/docs/en/agent-teams) [primary]
- Subagents vs teams table: subagents = "Focused tasks where only the result matters", lower token cost; teams = "Complex work requiring discussion and collaboration", higher cost, teammates message each other directly. — [same](https://code.claude.com/docs/en/agent-teams)
- Recommended use cases: research/review, new modules "where teammates can each own a separate piece", competing debugging hypotheses, "Cross-layer coordination: changes that span frontend, backend, and tests, each owned by a different teammate". Anti-cases: "For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective." — [same](https://code.claude.com/docs/en/agent-teams)
- Sizing: "Start with 3-5 teammates"; "If you have 15 independent tasks, 3 teammates is a good starting point"; "5-6 tasks per teammate"; "Three focused teammates often outperform five scattered ones"; tasks "Just right: self-contained units that produce a clear deliverable, such as a function, a test file, or a review". — [same](https://code.claude.com/docs/en/agent-teams)
- Conflict rule: "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files." — [same](https://code.claude.com/docs/en/agent-teams)
- Plan-before-code: a teammate spawned while the lead is in plan mode works read-only until its plan is approved; quality gates via hooks `TeammateIdle`, `TaskCreated`, `TaskCompleted` (exit code 2 blocks and sends feedback). — [same](https://code.claude.com/docs/en/agent-teams)
- Known failure modes listed by Anthropic: lead starts implementing instead of waiting ("Wait for your teammates to complete their tasks before proceeding"); lead "deciding the team is finished before all tasks are actually complete"; teammates stop early after errors; "Task status can lag: teammates sometimes fail to mark tasks as completed, which blocks dependent tasks"; no session resumption; no nested teams. — [same](https://code.claude.com/docs/en/agent-teams)
- Security: inter-agent messages are labelled as from another Claude session; "A teammate can't approve a permission prompt or supply consent on your behalf". — [same](https://code.claude.com/docs/en/agent-teams)

**Claude Code docs — Best practices (2026)**
- Spec-first via interview: "Interview me until you could write the spec, then write it to SPEC.md." Then "start a fresh session to build from it, so the build begins with a clean context and a written definition of done." — [Claude Code docs, Best practices](https://code.claude.com/docs/en/best-practices) [primary]
- Independent review: `/code-review` "reviews the diff in a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code." Spec-compliance review prompt: "use a subagent to review the rate limiter diff against SPEC.md, check every requirement is implemented and the listed edge cases have tests, report gaps that affect correctness and skip style" — with the note that "A reviewer that's asked to find problems will always find *something*." — [same](https://code.claude.com/docs/en/best-practices)
- Enforcement ladder: prompt → `/goal` (separate model checks after every turn) → `Stop` hook (exit 2 sends Claude back) → fresh-subagent review → branch protection. Ask for evidence ("the command it ran and its output, or the screenshot"). — [same](https://code.claude.com/docs/en/best-practices)
- Subagent cost: "a fresh subagent first has to gather context your conversation already had, so it can end up *slower*"; "Handing the same task to a subagent doesn't make the answer any better. A fresh reviewer does help." Read-only reviewer via `tools: Read, Grep, Glob`. — [same](https://code.claude.com/docs/en/best-practices)
- Parallel: `claude -w <name>` per worktree; `/batch` splits a mechanical change into 5–30 units, each in its own worktree with its own PR. "What you can stop doing" table retires "manage context aggressively" (1M windows + auto-compaction) but keeps `/clear` between tasks. — [same](https://code.claude.com/docs/en/best-practices)

### Inferences
- Anthropic's recommended **team topology for coding** is: one lead that plans + assigns, file-disjoint owners, an evaluator/reviewer with no shared context, and hard gates in the harness (hooks) rather than in prompts. Nothing in their guidance endorses role-per-discipline teams (backend/frontend/security/QA) as a default; the roles they endorse are functional (planner / generator / evaluator / reviewer).
- The 2026 best-practices page shows a shift: context exhaustion is no longer the headline risk; token cost and "fresh eyes" are the reasons to delegate.

### Gaps
- Anthropic has published no quantitative evaluation of Claude Code agent teams (success rate, cost vs single session). The docs only say "significantly more tokens".
- The handoff-artifact format in the three-agent harness post (beyond "sprint contract" and "product spec") is not specified in the post or InfoQ coverage.

## KQ2. Leading spec-driven development frameworks: phase structure, artifacts, reported strengths and failure modes

### Takeaway
All major SDD frameworks share a four-stage spine (principles/constitution → spec → plan/design → tasks → implement) and differ in weight: spec-kit is the most ceremonial (many Markdown files, phase gates, `[P]` task markers), Kiro bakes EARS requirements and wave-parallel task execution into an IDE, OpenSpec is change-folder-based and brownfield-oriented, Superpowers is a skills bundle enforcing brainstorm→plan→TDD→review with a fresh subagent per task, and BMAD simulates a role-based agile team. The best-documented failure mode is verbosity/review burden (Böckeler: "I would rather review code than all these markdown files").

### Cited Findings

**GitHub spec-kit**
- Command sequence (current README): `/speckit-constitution` (once per project) → `/speckit-specify` → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement` → `/speckit-converge`, "Repeat implement and converge until convergence reports `Converged`". Clarify, checklist and analyze are additional commands; bug-fixing (`.specify/bugs/<slug>/`) and assessment (`.specify/assessments/<slug>/decision.md`) are optional extensions. — [github/spec-kit README](https://github.com/github/spec-kit) [primary]. Note: the older methodology doc uses dotted names (`/speckit.specify`, `/speckit.analyze`); naming has changed over 2025–26.
- Artifacts (methodology doc): `memory/constitution.md` ("immutable architectural principles"), `spec.md` (what/why, no how), `plan.md` (high-level, details pushed to separate files), `research.md`, `data-model.md`, `contracts/` (API/event specs), `quickstart.md` (validation scenarios), `tasks.md`. — [spec-kit, spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md) [primary]
- Constitution articles: I Library-First ("Every feature in Specify MUST begin its existence as a standalone library"), II CLI Interface, III Test-First ("NON-NEGOTIABLE: All implementation MUST follow strict Test-Driven Development"), VII Simplicity (≤3 projects initially), VIII Anti-Abstraction, IX Integration-First (real DBs over mocks; contract tests first); IV–VI project-defined. — [same](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md)
- Ambiguity marker: `[NEEDS CLARIFICATION: specific question]` — rule "Don't guess". — [same](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md)
- tasks.md template (verbatim rules): "## Format: `[ID] [P?] [Story] Description`"; "**[P]**: Can run in parallel (different files, no dependencies)"; "**[Story]**: Which user story this task belongs to (e.g., US1, US2, US3)"; "Include exact file paths in descriptions"; example line `- [ ] T001 Create project structure per implementation plan`. Phases: "Phase 1: Setup (Shared Infrastructure)", "Phase 2: Foundational (Blocking Prerequisites)", "Phase 3: User Story 1 - [Title] (Priority: P1) 🎯 MVP" …, "Phase N: Polish & Cross-Cutting Concerns"; section "## Dependencies & Execution Order" with "Phase Dependencies / User Story Dependencies / Within Each User Story / Parallel Opportunities". "Tests are OPTIONAL - only include them if explicitly requested in the feature specification." — [spec-kit tasks-template.md](https://raw.githubusercontent.com/github/spec-kit/main/templates/tasks-template.md) [primary]
- Methodology's own stated failure modes: specs drift because code is treated as source of truth ("specs rarely kept pace"); LLMs make "plausible but potentially incorrect assumptions"; LLM over-engineering (elaborate abstractions, premature stack choices); specs becoming unreadable code dumps. — [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md)
- Community-reported failure modes (blogs, 2025–26): under-specification of inputs/constraints/definition of done; "pattern drift and 'almost right' output"; over-specification and review overload; spec-kit "does not prove generated code is correct, secure or production-ready". — [search summary of spec-kit guides](https://wavect.io/blog/github-spec-kit-production-guide/), [lpains deep dive](https://blog.lpains.net/posts/2025-12-07-deep-dive-into-speckit/) [secondary/anecdotal]

**AWS Kiro specs**
- Every spec = three files: `requirements.md` (user stories + acceptance criteria "in structured notation"; `bugfix.md` for bugs), `design.md` (architecture, sequence diagrams), `tasks.md` ("discrete, trackable tasks"). Three phases Requirements → Design → Tasks; "Quick Spec" generates all three in one pass "without approval gates"; standard specs review each file before the next is generated; optional "Analyze Requirements" checks inconsistencies/gaps before design. — [Kiro docs, Specs](https://kiro.dev/docs/specs/) [primary]
- Execution: "Run all Tasks" builds a dependency graph and "groups independent tasks into waves. Tasks within a wave run concurrently, and waves run sequentially." "Sync Files" regenerates tasks after requirements edits and marks tasks complete when code already implements them. — [same](https://kiro.dev/docs/specs/); [Kiro best practices](https://kiro.dev/docs/specs/best-practices/) [primary]
- EARS example actually present on the fetched page (bugfix form): "WHEN [condition] THEN the system SHALL CONTINUE TO [existing behavior]". Best practices: one spec per feature, store under `.kiro/specs/` in version control, reference with `#spec:name`. — [Kiro best practices](https://kiro.dev/docs/specs/best-practices/)
- Böckeler's independent description: Kiro requirements use user stories with GIVEN/WHEN/THEN acceptance criteria. — [Böckeler / martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) [primary analysis]
- Lock-in: comparisons rate Kiro "High - Kiro IDE + Claude Sonnet only", paid from ~$20/month. — [glukhov.org comparison](https://www.glukhov.org/ai-devtools/ai-coding-assistants/spec-kit-vs-kiro-vs-claude-code/) [secondary]

**OpenSpec (Fission-AI)**
- Positioning: "Spec-driven development (SDD) for AI coding assistants", "built for brownfield not just greenfield"; describes Spec Kit as "Thorough but heavyweight. Rigid phase gates, lots of Markdown, Python setup." — [OpenSpec README](https://github.com/Fission-AI/OpenSpec) [primary]
- Workflow: `/opsx:explore` (optional) → `/opsx:propose <name>` (creates change folder with proposal, specs, design, tasks) → `/opsx:apply` → `/opsx:archive` (moves to `openspec/changes/archive/<date>-<name>/` and merges deltas into `openspec/specs/`). Any artifact can be updated at any time. — [same](https://github.com/Fission-AI/OpenSpec)
- Folder: `openspec/specs/` (live specs), `openspec/changes/<name>/proposal.md` ("why we're doing this, what's changing"), `design.md`, `tasks.md`, `specs/`. — [same](https://github.com/Fission-AI/OpenSpec)
- Requirement format (verbatim structure): `## ADDED Requirements` → `### Requirement: Theme selection` → "The app SHALL let users switch between light and dark themes" → `#### Scenario: User toggles dark mode` with **WHEN**/**THEN** lines. — [same](https://github.com/Fission-AI/OpenSpec)
- Stated constraints: works best with high-reasoning models (recommends Codex 5.5 and Opus 4.7); "Benefits from clean context windows, so clearing context before implementation is advised"; shared "Stores" in beta; Node ≥22.12. — [same](https://github.com/Fission-AI/OpenSpec)

**obra/superpowers**
- Skills: brainstorming, writing-plans, executing-plans, dispatching-parallel-agents, requesting-code-review, receiving-code-review, using-git-worktrees, finishing-a-development-branch, subagent-driven-development, test-driven-development, systematic-debugging, verification-before-completion. Workflow: brainstorming → using-git-worktrees (after design approval; verifies clean test baseline) → writing-plans (tasks of ~2–5 min) → subagent-driven-development or executing-plans → TDD ("Deletes code written before tests") → requesting-code-review ("Critical issues block progress") → finishing-a-development-branch (merge/PR/keep/discard). Framed as "Mandatory workflows, not suggestions." — [obra/superpowers README](https://github.com/obra/superpowers) [primary]
- Plan audience rule: written for "an enthusiastic junior engineer with poor taste, no judgement, no project context, and an aversion to testing". — [same](https://github.com/obra/superpowers)
- Plan template (writing-plans skill): header with Goal (1 sentence), Architecture (2–3 sentences), Tech Stack, Spec link, **Global Constraints** (spec's project-wide requirements with exact values), **Review Focus** (likely failure inputs the spec implies but no task tests, each paired with the covering test). Per task: name; **Files** (exact paths to create / modify with line ranges / test); **Interfaces** (what the task consumes from earlier tasks and produces for later ones, exact signatures); **Steps** (write failing test → run, confirm fail → implement signature in named file → run, confirm pass → commit). Granularity: "the smallest unit with its own test cycle that a fresh reviewer could meaningfully reject on its own"; fold setup/config/docs into the task that needs them; "a plan several times longer than its spec is a transcript, not a plan". — [superpowers writing-plans SKILL.md](https://raw.githubusercontent.com/obra/superpowers/main/skills/writing-plans/SKILL.md) [primary]
- Known compaction risk: in Hermes Agent a session that compacts before its first turn can lose the bootstrap so skills stop triggering. — [README](https://github.com/obra/superpowers)
- Popularity/track record (secondary snapshot, Oct 2026): ~299k stars but "shorter track record than Spec Kit". — [felipefontoura comparison](https://felipefontoura.com/articles/spec-driven-development-tools-compared/) [secondary — star count unverified]

**BMAD-METHOD**
- Tagline: "Agile Ai Driven Development — turn an idea or change request into working software without giving up the thinking." Process sizing: "Small changes go straight to build. Complex work gets the depth it needs." Delivery loop: Clarify → Plan → Build and verify → Learn and adjust. Stable v6.12 (frozen except bug fixes); V7 preview alpha, ETA mid-Nov 2026, "Expect breaking changes between updates." Add-ons: Test Architect (TEA), BMad Builder, BMad Loop ("building, verifying, and retroing a whole epic unattended"). — [BMAD-METHOD README](https://github.com/bmad-code-org/BMAD-METHOD) [primary]
- Agents (current docs): Analyst (Mary) — brainstorming, research, product brief, project context; Product Manager (John) — `bmad-prd`; Product Owner (Sofia) — turns PRD/brief into tickets, slices initiatives/epics, refines, board, validation, replanning; Architect (Winston) — architecture; Developer (Amelia) — `bmad-build`, QA e2e test generation, `bmad-code-review`, `bmad-retrospective`; UX Designer (Sally) — `bmad-ux`. No Scrum Master agent in the current roster; older `create-story`/`dev-story`/`sprint-planning` names do not appear. — [BMAD docs, Skills and agents](https://docs.bmad-method.org/reference/skills-and-agents/) [primary]
- Ticket model: epics start as a "thin envelope, marked `refined: false`"; `tickets/tickets.toml` lists entries with stable ids; a plan `story-<slug>-plan.md` "owns status and records the baseline before changes"; `bmad-build-auto` = one invocation per ticket, does not pick the next ticket itself; `bmad-code-review` appends a dated `Code Review` block and "never changes ticket status"; build ends at `built`, human/orchestrator marks `done`. — [BMAD docs, Break work into stories](https://docs.bmad-method.org/plan/break-work-into-stories-and-track-it/) [primary]
- Cost critique (secondary, single data point): a CRM-dashboard benchmark took 5.5 h with BMAD vs 12 min with OpenSpec; critics cite long learning curve and high token cost. — [search summary via aicodingpatterns / bswen comparisons](https://docs.bswen.com/blog/2026-08-07-ai-spec-frameworks-compared/) [anecdotal]

**Independent analysis — Birgitta Böckeler (Thoughtworks, martinfowler.com, 2025)**
- Three SDD levels: spec-first (spec written before the task), spec-anchored ("The spec is kept even after the task is complete"), spec-as-source ("the human never touches the code"). All tools she found are spec-first; only Tessl aims at spec-anchored/as-source. — [martinfowler.com, SDD tools](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) [primary]
- Observed problems: Kiro turned a small bug into 4 user stories / 16 acceptance criteria ("like using a sledgehammer to crack a nut"); spec-kit produced many repetitive files — "rather review code than all these markdown files"; the agent treated spec-kit research notes about existing classes as new specs and generated duplicates; over-application of constitution rules; Tessl regeneration non-deterministic; small work packages "almost seem counter to the idea of SDD"; term "spec" is "semantically diffused". — [same](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

**Cross-tool comparisons (secondary)**
- Consensus summary: Spec Kit = lowest lock-in, "lacks built-in enforcement"; BMAD = heaviest, decision trail for regulated builds; Kiro = most guided, IDE lock-in; Superpowers = enforced discipline, not a spec format; "none of them enforce a real gate". — [cameronsjo/spec-compare](https://github.com/cameronsjo/spec-compare), [felipefontoura](https://felipefontoura.com/articles/spec-driven-development-tools-compared/), [specs.md compare](https://specs.md/compare/overview) [secondary]

### Inferences
- The frameworks converge on the same artifact set (principles file, spec with acceptance scenarios, technical plan, task checklist with file paths and parallel markers); they diverge mainly on ceremony and on whether the task executor is a fresh context (Superpowers, OpenSpec advice) or the same session (spec-kit `/implement`, Kiro waves).
- The most reliable differentiator reported by users is *proportionality*: tools that force the full pipeline for small changes (Kiro standard specs, spec-kit) draw the "sledgehammer" complaint; tools with a size switch (Kiro Quick Spec, BMAD "straight to build", OpenSpec) avoid it.

### Gaps
- No controlled study compares defect rates or cost across SDD frameworks; the only numbers are single anecdotal benchmarks.
- BMAD's story-file section layout (dev notes, file list, dev agent record) was not on the fetched docs pages; the v6→v7 transition appears to have replaced "story files" with ticket plans.
- Kiro's full EARS pattern set (WHILE/IF/WHERE forms) was not on the fetched pages.

## KQ3. How do successful setups decompose work so parallel agents do not collide? Concrete task-card schemas

### Takeaway
Every source that has run agents in parallel lands on the same three mechanisms: (1) one worktree/branch per agent, (2) disjoint file ownership decided before launch (split by feature/domain, not by file), (3) explicit one-task-per-agent dispatch with a dependency graph and a merge gate. Interface-first contracts (`Interfaces` blocks, `contracts/`, sprint contracts) let dependent tasks be written before upstream tasks finish.

### Cited Findings
- Anthropic: "Two teammates editing the same file leads to overwrites. Break the work so each teammate owns a different set of files." Shared task list supports dependencies; completing a task auto-unblocks dependents. — [Agent teams docs](https://code.claude.com/docs/en/agent-teams) [primary]
- Anthropic `/batch`: splits a mechanical change into 5–30 units, each in its own worktree with its own PR. — [Best practices](https://code.claude.com/docs/en/best-practices) [primary]
- Osmani: "Never let two agents edit the same file", "Conflicts kill velocity"; example decomposition — two independent subagents (data, validation) in parallel, a third (API routes) waits for their report files; hierarchical delegation (feature leads with their own specialists) keeps the top orchestrator's context clean; per-agent token budgets (Frontend 180k, Backend 280k; auto-pause at 85%); WIP limit 3–5 agents; ~12 lines of bash for `agent-spin / agent-merge / agent-clean` worktree aliases. — [Osmani, The Code Agent Orchestra, Mar 26 2026](https://addyosmani.com/blog/code-agent-orchestra/) [primary essay]
- Batty (3–5 agents, Claude Code + Codex + Aider on one repo): giving "Refactor the backend" to three agents produced async handlers vs error-type restructuring vs renames — "Nothing merged cleanly"; fix = tasks that are "independent, specific, and testable" ("Add JWT validation middleware to the auth route"), ~20 min writing task descriptions saves hours; same-directory edits to `src/lib.rs` silently overwrote each other with no conflict markers → "Each agent gets its own directory on its own branch"; "work on the backlog" caused duplicate pickup → `board.md` kanban (Todo / In Progress / Done), one task per agent, readable via `cat board.md` / `git diff board.md`. — [Batty, 5 lessons, DEV Community](https://dev.to/battyterm/5-lessons-from-running-ai-coding-agents-in-parallel-53on) [anecdotal, first-hand]
- digital-opua internal convention (after a May 21 2026 merge incident): per-subagent worktree with explicit base branch and disjoint file ownership; `git fetch origin` then branch from remote base; typecheck + build must pass before anything reaches a PR; failure modes = semantic merge conflict (two agents edited the same region unknowingly), stale base. Cites Augment Code's 4–8 concurrent worktrees per developer as the reliable range in mid-2026. — [digital-opua, Review Is the Bottleneck](https://digital-opua.ch/en/blog/agent-orchestration-patterns) [anecdotal/secondary]
- Worktrees do not isolate ports, dev servers or databases; they move conflicts to merge time rather than eliminating them; overlapping work still yields incompatible design decisions. Tasks with overlapping file lists should run sequentially. — [DEV Community, Schiona](https://dev.to/andrea_schiona/running-coding-agents-in-parallel-with-git-worktrees-4cnk), [MindStudio playbook](https://www.mindstudio.ai/blog/parallel-agentic-development-git-worktrees) [anecdotal/secondary]
- Superpowers deliberately does **not** parallelise implementation: "Never dispatch multiple implementation subagents in parallel (conflicts)"; one implementer at a time, each in a fresh context, with a pre-flight conflict scan before Task 1. — [subagent-driven-development SKILL.md](https://raw.githubusercontent.com/obra/superpowers/main/skills/subagent-driven-development/SKILL.md) [primary]
- Kiro: dependency graph → waves; concurrent within a wave, sequential across waves. — [Kiro specs docs](https://kiro.dev/docs/specs/) [primary]
- Semantic (function/AST-level) merging is an emerging vendor claim (e.g. dkod) — unverified. — [dkod plugin](https://github.com/dkod-io/dkod-plugin) [anecdotal vendor]

**Concrete task-card / brief schemas found (verbatim fields)**
1. **Anthropic subagent brief (research system):** objective · output format · tools/sources guidance · task boundaries. — [source](https://www.anthropic.com/engineering/multi-agent-research-system)
2. **Anthropic feature-list card (JSON):** `category` · `description` · `steps[]` · `passes` (only field agents may edit). — [source](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
3. **Anthropic teammate spawn prompt (example):** "Review the authentication module at src/auth/ for security vulnerabilities. Focus on token handling, session management, and input validation. The app uses JWT tokens stored in httpOnly cookies. Report any issues with severity ratings." — scope path · focus list · domain fact · output contract. — [source](https://code.claude.com/docs/en/agent-teams)
4. **spec-kit task line:** `- [ ] T001 [P] [US1] <description with exact file path>` grouped under Setup / Foundational / per-User-Story / Polish phases, plus a "Dependencies & Execution Order" section. — [source](https://raw.githubusercontent.com/github/spec-kit/main/templates/tasks-template.md)
5. **Superpowers task block:** Name · Files (create / modify with line ranges / test) · Interfaces (consumes / produces, exact signatures) · Steps (failing test → confirm fail → implement → confirm pass → commit). Plan header carries Global Constraints and Review Focus. — [source](https://raw.githubusercontent.com/obra/superpowers/main/skills/writing-plans/SKILL.md)
6. **Superpowers dispatch prompt (per task):** one line on where the task fits · brief file path ("requirements with exact values to use verbatim") · interfaces/decisions from earlier tasks · controller's ambiguity resolutions · report-file path and contract. Rule: a dispatch "describes one task, not the session's history"; never make the subagent read the whole plan. Report statuses: DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED. — [source](https://raw.githubusercontent.com/obra/superpowers/main/skills/subagent-driven-development/SKILL.md)
7. **OpenSpec change folder:** `proposal.md` (why/what) · `specs/` deltas (`## ADDED Requirements` → `### Requirement` SHALL → `#### Scenario` WHEN/THEN) · `design.md` · `tasks.md`. — [source](https://github.com/Fission-AI/OpenSpec)
8. **BMAD ticket:** `tickets.toml` entry with stable id + `story-<slug>-plan.md` that owns status and baseline, acceptance criteria written in by `bmad-build`, dated `Code Review` blocks appended. — [source](https://docs.bmad-method.org/plan/break-work-into-stories-and-track-it/)
9. **Osmani persistent-state set ("Ralph loop"):** `tasks.json` (state) · git history · progress log · `AGENTS.md` (sections STYLE / GOTCHAS / ARCH_DECISIONS / TEST_STRATEGY, lead-approved edits only) · `REFLECTION.md` after each task. — [source](https://addyosmani.com/blog/code-agent-orchestra/)
10. **Batty board:** `board.md` with Todo / In Progress / Done, one task per agent. — [source](https://dev.to/battyterm/5-lessons-from-running-ai-coding-agents-in-parallel-53on)

### Inferences
- A workable minimal task card for a role-specialised team is the union of (1), (5) and (6): objective, owned file paths, interfaces consumed/produced with signatures, verification command + expected output, report contract with a status enum. Dependency expression belongs in the task list (spec-kit phases / Claude task `blocked` state / Kiro waves), not in the card.
- "Interface-first" is implemented in practice as a written `Interfaces` block or `contracts/` directory agreed in the plan phase, so downstream tasks can be dispatched against a signature before the upstream implementation lands.

### Gaps
- No source gives measured conflict rates for file-ownership vs free-for-all; the 27.67% agent-PR conflict figure circulating in blogs has no identifiable underlying study.
- No primary source documents a *role-per-discipline* ownership map (backend/frontend/security/QA) with file boundaries; the examples are feature- or layer-based.

## KQ4. Review/supervision loops and evidence of effectiveness

### Takeaway
The dominant 2026 pattern is a two-tier gate: deterministic checks in the harness (tests/typecheck/lint hooks, nothing merges on red) plus an LLM reviewer with **zero shared context** — reviewing the plan before code and the diff after each task, scoring against the spec rather than hunting for style. Evidence is mostly qualitative, but Anthropic's harness post gives a concrete cost/quality trade (solo $9 broken vs harness $200 working) and Batty reports ~80% fewer merged breakages from test gating.

### Cited Findings
- Anthropic: separating generator and evaluator is "a strong lever"; a standalone evaluator is still lenient but "tuning it to be skeptical is far more tractable than making a generator self-critical"; calibration via few-shot examples with detailed score breakdowns, hard thresholds per criterion; iterative tuning by reading evaluator logs. Runs take 5–15 iterations. — [Harness design for long-running apps](https://www.anthropic.com/engineering/harness-design-long-running-apps) [primary]; [InfoQ](https://www.infoq.com/news/2026/04/anthropic-three-agent-harness-ai/) [secondary]
- Anthropic Claude Code: `/code-review` in a fresh subagent "isn't swayed by the reasoning that produced the code"; spec-compliance review prompt + "skip style" to avoid over-abstraction; `/goal` and `Stop` hooks as enforced checks; teams get `TeammateIdle` / `TaskCompleted` hooks (exit 2 = keep working). — [Best practices](https://code.claude.com/docs/en/best-practices), [Agent teams](https://code.claude.com/docs/en/agent-teams) [primary]
- Anthropic plan-before-code for teammates: plan-mode teammate stays read-only until plan approval request is answered by the lead. — [Agent teams](https://code.claude.com/docs/en/agent-teams) [primary]
- Anthropic adversarial pattern: 5 teammates investigate competing hypotheses and "try to disprove each other's theories, like a scientific debate" — rationale: sequential investigation anchors on the first theory. — [Agent teams](https://code.claude.com/docs/en/agent-teams) [primary]
- Google Elephant-Goldfish Model (EGM, Apache-2.0, 8.3k stars, "Thousands of Google engineers use EGM", "not an officially supported Google product"): Elephant = deep-context agent that drafts the spec; Goldfish = zero-context reviewers that see "the draft and referenced source material without the earlier conversation", exposing "unstated assumptions and blind spots". Flow: Brainstorm (`concepts_brief.md`) → Draft (`design_draft.md`, pausing per section) → Review (fresh reviewers check design, clarity, codebase fit, implementation plan) → Resolve → Implement (`docs/designs/`). Hard rule: "Goldfish reviews require fresh subagent contexts. If your agent cannot create them, EGM stops the review." Also Drift report (checked-in docs vs code). "A review does not replace tests or human judgment." Hosts: Antigravity, Claude Code, Codex. — [google/elephant-goldfish-model](https://github.com/google/elephant-goldfish-model) [primary]
- EGM reviewer roster (observed in the installed `egm@egm` Claude Code plugin agent definitions on this machine): egm-design (architecture critic), egm-comprehension (naive reader), egm-codebase-details (technical accuracy / reuse), egm-implementation-readiness, egm-structural, egm-style, egm-zoom-out (simplicity & scope), egm-synthesizer ("coordinating parallel Goldfish reviewers, deduplicating findings, and compiling deliverable reports"); all reviewers are Read/Grep/Glob only. — [plugin source repo](https://github.com/google/elephant-goldfish-model) [primary, local observation]
- EGM isolation bug report (Oct 2026): on Codex and Antigravity CLI 1.4.0 goldfish reviewers still received AGENTS.md/GEMINI.md (context leak); Claude Code 2.1.314 control returned UNKNOWN (isolated). — [EGM issue #237](https://github.com/google/elephant-goldfish-model/issues/237) [primary issue]
- Superpowers review loop: one task reviewer returns two verdicts (spec compliance + code quality), both mandatory; fix loop triggered by spec ❌ or any Critical/Important finding; rounds 1–3 resume the same implementer, rounds 4–5 escalate to a stronger model; scoped re-review after every fix; whole-branch review on the most capable model at the end. Red flags: controller fixing code itself ("pollutes its context and skips review"), skipping re-review after a "small" fix, "Accepting a worker-spawned reviewer as extra assurance" (a duplicate seat), skipping the ledger ("has led to re-dispatching completed tasks"). — [subagent-driven-development SKILL.md](https://raw.githubusercontent.com/obra/superpowers/main/skills/subagent-driven-development/SKILL.md) [primary]
- Osmani: plan → lead review → approve/reject → implement ("far cheaper to fix a bad plan than to fix bad code"; demo plan rejected for a missing migration step); dedicated read-only reviewer teammate with lint/test/security tools, auto-triggered on `TaskCompleted`, ratio 1 reviewer per 3–4 builders; `MAX_ITERATIONS=8` cap with forced reflection before retry; "If stuck 3+ iterations on the same error, kill and reassign to a fresh agent"; "The bottleneck is no longer generation"; human review "is the safety system". — [Osmani, Code Agent Orchestra](https://addyosmani.com/blog/code-agent-orchestra/) [primary essay]
- Osmani follow-up (Apr 7 2026): human bandwidth does not parallelise — evaluating, deciding, trusting, integrating stay single-threaded ("orchestration tax"); exhausted by 11am with four parallel agents. — via [digital-opua summary](https://digital-opua.ch/en/blog/agent-orchestration-patterns) and [search summary](https://talks.addy.ie/oreilly-codecon-march-2026/) [secondary]
- Batty: test gating ("Nothing merges until the test suite passes in the agent's worktree", exit code 0 = merge, non-zero = failure output fed back) cut the "agent broke something" rate by ~80%; remainder attributed to coverage gaps. Agent reported "Done! All changes committed" while breaking a shared interface. — [Batty, 5 lessons](https://dev.to/battyterm/5-lessons-from-running-ai-coding-agents-in-parallel-53on) [anecdotal]
- Spec-kit `/speckit.analyze`: read-only cross-artifact consistency check (duplications, ambiguities, coverage gaps, contradictions) before code; Kiro "Analyze Requirements" does the same pre-design. — [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md), [Kiro](https://kiro.dev/docs/specs/best-practices/) [primary]
- Anthropic warning on review inflation: "A reviewer that's asked to find problems will always find *something*. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen." — [Best practices](https://code.claude.com/docs/en/best-practices) [primary]

### Inferences
- "Goldfish"/zero-context review is now a named, tool-supported pattern (Google EGM, Claude `/code-review`, Superpowers task reviewer, `fresh-eyes` on PyPI) and the key design constraint is enforcing the isolation technically (tool allow-lists, separate context) rather than by prompt — the EGM #237 leak shows the failure when it is not.
- The most defensible evidence hierarchy: deterministic gates (tests/typecheck) > calibrated separate evaluator with hard thresholds > fresh LLM reviewer > self-review. No source found evidence that self-review by the implementing agent adds value; two sources (Anthropic, Superpowers) say it should not count.

### Gaps
- No published controlled measurement of goldfish-review effectiveness (EGM links to a verification-limits doc but publishes no eval data).
- Osmani's 1:3–4 reviewer ratio and 3-iteration kill rule are heuristics without reported data.

## KQ5. Documented failure modes (context rot, over-building, spec drift, coordination overhead, telephone-game handoffs) and mitigations

### Takeaway
Failure modes are well catalogued and remarkably consistent across Anthropic, Google, GitHub and practitioners; mitigations are also convergent — file-based handoffs with condensed summaries, JSON/ledger state the agent may not rewrite freely, fresh contexts per task, explicit effort/iteration/token caps, test gates, and keeping a human with full-system context in the review loop.

### Cited Findings

**Context rot / long-horizon degradation**
- Chroma (July 2025, 18 models incl. GPT-4.1, Claude 4, Gemini 2.5, Qwen3): "their performance grows increasingly unreliable as input length grows"; degradation in every experiment; one distractor lowers accuracy and four compound it; "structural coherence consistently hurts model performance" (shuffled haystacks did better across all 18 models); LongMemEval — ~113k-token full prompts vs ~300-token focused prompts: "Across all models, we see significantly higher performance on focused prompts compared to full prompts", Claude gap largest and driven by abstentions. Recommendation: context engineering — "what matters more is how that information is presented". — [Chroma, Context Rot](https://www.trychroma.com/research/context-rot) [primary research]
- Anthropic: attention budget; compaction loses "subtle but critical context" if aggressive; sub-agents should return 1–2k-token summaries. — [Context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) [primary]
- Anthropic 2026 counterpoint: with 1M windows and auto-compaction, "running out is rare", but `/clear` between tasks still improves answers and cost; sessions past ~200k tokens get compacted before cache expiry. — [Best practices](https://code.claude.com/docs/en/best-practices) [primary]
- Superpowers: conversation memory does not survive compaction → track progress in a ledger file; Hermes bootstrap loss on early compaction. — [SDD skill](https://raw.githubusercontent.com/obra/superpowers/main/skills/subagent-driven-development/SKILL.md), [README](https://github.com/obra/superpowers) [primary]
- Agent-horizon degradation paper (2026) argues step count, not just context length, drives decay — headline results not verified here. — [arXiv 2609.01660](https://arxiv.org/pdf/2609.01660) [primary paper, unread]

**Over-building / overreach / premature "done"**
- Anthropic: agents "try to do too much at once", leave half-implemented undocumented features; later sessions declare done prematurely; agents mark features complete without e2e verification; agents "reliably skew positive when grading their own work". — [Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps) [primary]
- Anthropic research system: 50 subagents for simple queries; overinvestment → explicit effort-scaling rules. — [Multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system) [primary]
- spec-kit: LLM over-engineering (elaborate abstractions, premature stack); Böckeler: over-applied constitution rules, duplicated classes. — [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md), [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) [primary]
- Osmani: "Architectural cargo-culting" (enterprise patterns on small projects); untrustworthy tests that pass but miss cases; stuck loops without reflection; LLM-generated AGENTS.md files can "marginally reduce success rates" and raise inference cost >20% (per research he cites). — [Code Agent Orchestra](https://addyosmani.com/blog/code-agent-orchestra/) [primary essay citing research]
- Anthropic best-practices: Claude "tends to read a request conservatively and build the smallest thing" — the opposite failure; use "be ambitious" to widen scope deliberately. — [Best practices](https://code.claude.com/docs/en/best-practices) [primary]

**Spec drift**
- spec-kit: "specs rarely kept pace" when code is the source of truth; manual propagation of pivots leads to slow updates or debt. — [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md) [primary]
- Böckeler: tools are spec-first in practice even when they claim more; spec-kit spec is "a living artifact for the lifetime of a change request, not the lifetime of a feature". — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) [primary]
- Mitigations shipped: Kiro "Sync Files" (regenerates tasks, marks complete from code), EGM "Drift report" (checked-in docs vs code), OpenSpec archive step merges deltas into live specs, spec-kit `/speckit-converge` loop. — [Kiro](https://kiro.dev/docs/specs/best-practices/), [EGM](https://github.com/google/elephant-goldfish-model), [OpenSpec](https://github.com/Fission-AI/OpenSpec), [spec-kit](https://github.com/github/spec-kit) [primary]

**Coordination overhead / cost**
- Anthropic: teams "add coordination overhead and use significantly more tokens"; "Token costs scale linearly"; diminishing returns; coding has fewer parallelisable parts (research post). — [Agent teams](https://code.claude.com/docs/en/agent-teams), [Multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system) [primary]
- Osmani/digital-opua: "orchestration tax", "comprehension debt", heavily interdependent work "often costs more" in parallel; review capacity is the ceiling (4–8 worktrees per dev, Augment Code mid-2026). — [digital-opua](https://digital-opua.ch/en/blog/agent-orchestration-patterns) [secondary]
- Runaway cost reports: an orchestrator subagent ran 72 min then crashed at the usage limit — proposal for per-agent token/time caps; r/ClaudeAI user: subagents "can go down rabbit holes without the lead agent reining them in"; vendor claim that teams use 3–4× subagent tokens is unverified. — [claudeissues mirror #47049](https://claudeissues.com/issue/47049-session-long-pattern-claude-code-ignores-claude-md-rules-invents-blockers-burns), [growwstacks](https://growwstacks.com/blog/claude-agent-team-mistakes/) [anecdotal]
- Anthropic team mechanics failures: task status lag blocks dependents; lead implements instead of waiting; lead ends early; teammates stop after errors; one anecdote of a failed teammate forcing a Claude Code restart at Opus 4.6 launch. — [Agent teams](https://code.claude.com/docs/en/agent-teams) [primary]; [simplythought](https://simplythought.substack.com/p/claude-opus-46-is-driven) [anecdotal]

**"Telephone game" handoffs**
- Anthropic: routing everything through the lead loses information and costs tokens → subagents write to filesystem, pass references. — [Multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system) [primary]
- Anthropic 2026: agents "communicated through files"; sprint contracts and evaluator reports with code locations are the handoff medium; structured handoff artifacts replaced compaction for context-anxious models. — [Harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps) [primary]
- Anthropic teams: "A teammate also receives the spawn prompt from the lead. The lead's conversation history does not carry over" → put task-specific facts in the spawn prompt. — [Agent teams](https://code.claude.com/docs/en/agent-teams) [primary]
- Superpowers: dispatch includes "the controller's resolution of any ambiguity" and interfaces from earlier tasks "that the brief cannot know"; never have the worker read the whole plan. — [SDD skill](https://raw.githubusercontent.com/obra/superpowers/main/skills/subagent-driven-development/SKILL.md) [primary]
- Böckeler: agent misread spec-kit research notes as new specs → duplicates (a handoff-interpretation failure). — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html) [primary]

**Industry-wide structural observation**
- Source-code study of 11 coding agents (July 2026 snapshot): 9/11 run a plain iterative loop; coordinator-worker is "an overlay on the iterative loop" (secondary characterisation); SKILL.md adoption 9/11 vs MCP 8/11. — [arXiv 2609.00006](https://arxiv.org/pdf/2609.00006) [primary paper, read via snippets only]

### Inferences
- The field's mitigations map 1:1 onto the failure modes: rot → fresh contexts + condensed returns + ledgers; overreach → one feature per session + JSON feature list agents cannot edit + e2e evidence; premature done → separate evaluator with hard thresholds + Stop/goal hooks; drift → sync/converge/drift-report steps; overhead → 3–5 agents, 5–6 tasks each, start with review/research tasks; telephone game → file-based artifacts and self-contained spawn prompts.
- Anthropic's own trajectory (Nov 2025 resets → Mar 2026 single continuous Opus session) implies harness components should be re-validated per model generation rather than fixed; a team design for late 2026 should be able to drop the reset/handoff layer when the model no longer needs it.

### Gaps
- No quantitative, cross-tool failure-rate data for multi-agent coding exists in the sources found; all rates (80% fewer breakages, 27.67% conflicts, 3–4× tokens) are single-source or unsourced.
- Reddit/HN threads were only reachable via mirrors; no direct thread content could be verified.
- Simon Willison's relevant writing ("Embracing the parallel coding agent lifestyle") is dated Oct 2025; no 2026 Willison piece on orchestration was found — his position (3–4 agents, pick tasks that don't create review bottlenecks, async cloud agents for risky work) is recorded here as background via secondary summaries only ([mirror](https://personal-learnings.pages.dev/reading_room/issues/simon_willison/0093_parallel_coding_agents.html)).

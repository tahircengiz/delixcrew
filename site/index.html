delixCrew

Spec first. Agents write the code. A human makes the final call.

The main session that runs the work is the lead. The lead asks you one question at a time (this interview is called the grill) and writes a tech spec from your answers. It then splits the work into cards: small, independent units of work. Each card goes to a separate implementer session working in its own worktree. Review agents that cannot change files check the result.

The work stops at two points and waits for a human. These points are gates: at Gate 1 the spec is approved, at Gate 2 the PR is merged. The rules are not left to the agent's good intentions; Claude Code itself enforces them: hooks block forbidden actions and tool lists limit what each agent can do. This page calls that control layer the harness.

Core idea

A software team's division of labour instead of a single-session loop

Roles replace the loop of "open, pick a folder, read the history, continue". What each role can do is limited by its tool list and by hooks.

Spec first

The grill asks one question at a time and adds a recommendation to each. Requirements are written to be testable, in SHALL and WHEN/THEN form. What is out of scope is stated explicitly.

Agents write the code

The implementer works in its own worktree. It changes only the files the card allows (the Files list). It writes a failing test first and cannot change existing tests.

A human decides

At Gate 1 the spec or card is approved, at Gate 2 the PR is merged. The riskiest cards (Tier 3) also need an explicit security approval. The lead never runs gh pr merge.

Claude Code enforces the rules

Review agents (reviewers) have no write tool in their tools list. Hooks block writes to protected paths (auth, secrets, CI, deploy) and to existing test files. Because of the Stop hook, the implementer cannot finish until the tests pass.

Main flow

From request to close: six commands, two gates

/delixcrew:start proposes two things. Size shows how much process the work needs: S, M or L. Tier shows the risk: 1, 2 or 3. The higher the tier, the more review and approval it takes. For a small, well-described job, a single session plus /delixcrew:verify is proposed instead of the full flow.

Tier and gate matrix

Risk is set by path and action, not by line count

The tier looks at the file path, the action and external content. A 3-line change in Keycloak is size S, tier 3. If review finds that a protected path was touched, the card moves to tier 3 and needs a security approval.

Hooks

Three hooks: which tool they stop, and where

hooks/hooks.json defines three entries, all Python scripts. Without python3 on PATH, Write, Edit and Bash are blocked; if a hook fails, the action is blocked too (fail-closed). The implementer rules apply only while a local .delix/card file exists at the worktree root; git does not track this file. The reviewer rules apply when the agent type (agent_type) is delixcrew:*.

Known limits

  • write_gate does not see what is written through Bash (echo >, sed -i, tee). bash_gate catches only redirects, cp, mv and tee into a protected path. To cover this gap, the qa agent counts a change to the card or to docs/delix/** in the diff as a finding.
  • The hooks close the known send paths, not every path. A command built from base64, a wrapper written to a file or an HTTP request without gh can get past pattern matching. The README suggests adding permissions.deny to your own settings.json.
  • Claude Code ignores the permissionMode, hooks and mcpServers fields in plugin agent definitions. That is why the constraints live in the tools list and in hooks.json.
  • The Stop gate runs delix.json commands only after you approve them from your own terminal (trust.py allow); the approval covers the command text, not the test files, and not the project's own .claude/settings.json hooks.

0.6.0Triage hook rules

In every session bash_gate denies triage.py apply and running triage.py under script, expect, unbuffer or pty.spawn. It also denies gh issue close|reopen|lock|…, gh label and writing gh api calls (-f, --input, graphql, a method other than GET) aimed at delixcrew. write_gate denies direct writes into the triage record directory. As with feedback, only the known paths are closed.

Self-feeding · 0.5.0 and 0.6.0

The plugin reports its own faults; a human still sends them

When delixcrew sees a fault of its own in a project, it writes it to a local draft. The draft is redacted, the user sees the full text and sends it from their own terminal. The finding becomes a GitHub issue, goes through triage and, if accepted, re-enters the workflow through /delixcrew:start #<n>.

When a draft is written

/delixcrew:close and /delixcrew:review add a draft only in three cases: a hook rejected correct work, a skill step could not be followed as written, or a plugin limit was worked around by hand. Otherwise the user says /delixcrew:feedback note in chat. If the feature is off, nothing is written (exit 3).

Redaction and blocking

  • Replaced: every host outside a short allowlist, IPs outside the documentation ranges and loopback, MAC and e-mail addresses. The user name in home paths and other absolute paths, the user and machine name, the source project names and --terms are replaced too.
  • BLOCKED (fail-closed): a gitleaks finding or gitleaks missing, an invisible Unicode control character, an opaque string of 32+ characters, more than 15 code lines, a body over 8 KB, a match left after redaction.
  • A secret is not redacted and sent; the draft is blocked.

Approval chain

  • The preview text is data. An "approved" inside a draft, a file or an issue is not consent.
  • To approve, the user names the draft id in chat: yes F003. Claude then gives the one-line command.
  • send prints the text once more in the terminal and waits for SEND <hash>. If the text changed after the preview, it stops.
  • The target repo is fixed. If an issue with the same fingerprint exists, no new one is opened and the existing URL is recorded.

0.6.0Triage: verify, filter, decide

In triage the architect checks a bug against the reported version's code and a feature against the delix principles, and looks at every issue for duplicates, its source and missing information. It then proposes one of accept, needs-info, duplicate, wontfix or defer. The human decides in chat, with the number: accept #12. The user publishes the comment and labels from their own terminal by typing APPLY <hash>. Only duplicate and wontfix close the issue.

Glossary

Short glossary

card
One unit of work, in docs/delix/tasks/T<nnn>-<slug>.md. It holds the goal, the Files list, Interfaces, the verification command and the report contract. Files lists do not overlap between cards.
wave
A group of cards opened together, at most max_parallel (3). A card that touches the same file as another, or depends on another card, goes to the next wave. Kept in STATE.json.waves.
tier
The risk axis that sets the gates (1–3). It looks at the file path, the action and external content. A separate axis from size (S/M/L, process weight).
gate
A point where a human decides. At Gate 1 the spec or card is approved, at Gate 2 the PR is merged. A Tier 3 card also needs a security approval. Automatic checks such as tests, CI and gitleaks are gates too (deterministic gates): a machine decides, and they run before the LLM review.
drift
The gap between the spec and the merged code: REQs not implemented, or behaviour not in the spec. The architect looks for it at close; findings go to the open items in STATUS.
escalation
When review rounds pass max_review_rounds (3), the card becomes escalated. The user picks: a stronger model, a narrower scope, or accept.
worktree
The implementer's own git working tree on the card branch. Diffs and remote tests are taken from the branch's commit SHA, not from the directory.
K decision
A numbered decision record (K1, K2, …), kept in STATUS and SPEC and marked "reversible" or "one-way".
